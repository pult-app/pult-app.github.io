## 1. Резюме

### 1.1 Проблема

Информация, по которой я каждый день принимаю решения, разбросана по восьми местам: два почтовых ящика, hh.ru, Telegram, расписание в ЛАД, Google Календарь, заметки Obsidian и сайты компаний. ИИ-агенты уже собирают её три раза в день, но складывают на страницу claude.ai (версия v0). У v0 нет своего API, нет пушей и нет офлайна. Ещё страница зависит от сессии claude.ai: 26.09.2026 база страницы была недоступна агенту около часа, и обновление встало.

### 1.2 Решение

PWA на телефон и ПК с экраном «Сегодня». На нём пары, срочные дела, ответы компаний и карточки для повторения. Данные лежат в своей базе Postgres (Supabase). ИИ-агенты пишут в неё через отдельный API с токенами и правами. О важном (приглашение, тест, вопрос работодателя) приходит пуш.

### 1.3 Критерии успеха

| Код | Метрика | Цель | Как меряем |
| --- | --- | --- | --- |
| K1 | Время от нажатия на иконку до экрана «Сегодня» с данными | не больше 3 с на 4G, LCP не больше 2,5 с | Lighthouse (мобильный профиль), 5 замеров |
| K2 | Задержка между письмом компании и записью в пульте | не больше 6 ч для писем, пришедших с 9:00 до 21:00 | `message.received_at` против `message.created_at` |
| K3 | Пропущенные дедлайны за семестр | 0 | все дедлайны из писем и учёбы есть в базе и получили напоминание за 24 ч |
| K4 | Время от записи приглашения агентом до пуша | не больше 5 мин | `notification.sent_at` против `message.created_at` |
| K5 | Стоимость в месяц | 0 ₽ | бесплатные тарифы Supabase и хостинга |
| K6 | Регулярность тренажёра в период собеседований | не меньше 3 сессий в неделю | `card_review`, группировка по дням |

## 2. Пользователи и функциональность

### 2.1 Персоны

**Герман, основной пользователь.** Студент 3 курса, ищет оплачиваемую стажировку системным аналитиком, параллельно учится на красный диплом. Утром институт, днём и вечером работа и учёба. Телефон iPhone, ПК Windows 11. Главный вопрос дня: «что у меня сегодня и что горит».

**ИИ-агент, системный актор.** Задачи по расписанию в Claude Code (`funnel-sync` 3 раза в день, `internship-scan` по понедельникам и четвергам). Читают почту, hh.ru и ЛАД, классифицируют и записывают результат в пульт. Ничего не отправляют от имени Германа.

### 2.2 Пользовательские истории

Приоритет по MoSCoW: M обязательно для MVP, S желательно в v1.1, C можно позже.

#### Эпик E1. Сегодня

**US-01 (M).** Как Герман, я хочу при открытии приложения видеть пары на сегодня, чтобы не открывать отдельно расписание.
- Экран «Сегодня» открывается первым после входа.
- Неделя определяется по правилам ЛАД. Числитель: учебная неделя, в которую попадает 1 сентября. Номер недели считается от понедельника этой недели, первая неделя имеет номер 1.
- Пара показывается, только если текущая неделя попадает в её диапазон «(с X по Y нед)», «(с X нед)», «(по Y нед)».
- Подгруппы показываются внутри одной пары с подписью «подгруппа 1», «подгруппа 2».
- Идущая сейчас пара подсвечена, прошедшие приглушены. Время берётся по Europe/Moscow.
- Если пар нет, показывается ближайший учебный день и время первой пары.

**US-02 (M).** Как Герман, я хочу видеть одним списком всё, что горит в ближайшие 3 дня, чтобы ничего не пропустить.
- В списке дедлайны вакансий, письма с дедлайном и без отметки «сделано», учебные работы не в статусе «сдано», дела без отметки «сделано».
- Сортировка по дате и времени. Просроченное и сегодняшнее выделено красным, 1-3 дня жёлтым.
- Отдельный блок «Дальше» на 4-14 дней.
- У каждого пункта есть переход к источнику (вакансия, письмо, работа).

**US-03 (M).** Как Герман, я хочу добавить дело со сроком за 10 секунд, чтобы не держать его в голове.
- Форма: что сделать (обязательно, до 200 символов), дата (по умолчанию сегодня), время (необязательно), тип: учёба, карьера, деньги, личное.
- Дело отмечается выполненным галочкой прямо в списке.

#### Эпик E2. Воронка стажировок

**US-04 (M).** Как Герман, я хочу видеть все вакансии по этапам воронки и менять статус в один тап, чтобы понимать, где я в поиске.
- Статусы: найдена, подана, тест, собеседование, оффер, резерв, отказ, не подходит. Переходы по диаграмме состояний в [processes.md](04-processes/processes.md).
- Счётчики по этапам: ждут подачи, подано, дошло до теста, до собеседования, офферы.
- Фильтр по статусу и поиск по компании.
- Каждая смена статуса пишется в историю с автором (Герман или агент).

**US-05 (M).** Как Герман, я хочу открыть вакансию и видеть все письма компании по ней, следующий шаг и к чему готовиться.
- В карточке: следующий шаг, подготовка, заметки, дедлайн, ссылка на вакансию, хронология писем.
- Изменения, которые сделал я, агент не перезаписывает (см. US-12).

**US-06 (S).** Как Герман, я хочу видеть отклики без ответа дольше 7 дней, чтобы вовремя напомнить о себе.
- Условие: статус «подана», с даты подачи прошло не меньше 7 дней, живых ответов нет, отметки «напомнил» за последние 7 дней нет.
- Кнопка «Напомнил о себе» ставит дату напоминания.

#### Эпик E3. Входящие

**US-07 (M).** Как Герман, я хочу видеть ответы компаний с сутью и действием, чтобы не читать каждое письмо целиком.
- Типы: приглашение, тестовое, оффер, отказ, вопрос, автоответ «получено», инфо.
- По умолчанию показываются письма, которые ждут действия. Автоответы вынесены в отдельный фильтр.
- Кнопки «Сделано» и «Вернуть».

#### Эпик E4. Учёба

**US-08 (M).** Как Герман, я хочу видеть учебные работы по предметам со сроками и статусами, чтобы сдавать без хвостов.
- Статусы: не начато, делаю, готово к сдаче, сдано.
- Сортировка: «делаю», потом «готово», потом «не начато», внутри по сроку.
- Путь к папке работы на ПК показывается текстом.

#### Эпик E5. Тренажёр

**US-09 (M).** Как Герман, я хочу повторять вопросы с собеседований карточками, чтобы закрывать пробелы до следующего собеса.
- Сначала видно только вопрос, ответ открывается кнопкой.
- «Знаю» переносит карточку в следующую коробку: интервалы 1, 3, 7, 14 дней. «Не знаю» возвращает её в коробку 0, повтор завтра.
- Фильтр по темам, счётчик карточек на сегодня.
- Каждый ответ пишется в историю повторений.

#### Эпик E6. Уведомления

**US-10 (S).** Как Герман, я хочу получать пуш о приглашении, тесте, оффере и вопросе работодателя, чтобы ответить в тот же день.
- Пуш уходит не позже 5 минут после записи письма (K4).
- Текст пуша одной строкой: компания и суть, например «Компания N: приглашение на техсобес 30.09 15:00».
- Утренний пуш в 8:00 со сводкой дня, если есть что-то срочное.
- В тихие часы 23:00-8:00 пуши, кроме оффера, копятся до утра.

#### Эпик E7. Агенты и API

**US-11 (M).** Как ИИ-агент, я хочу записывать вакансии, письма, работы, дела, карточки и расписание через API с токеном, чтобы не зависеть от сессии claude.ai.
- У каждого агента свой токен и набор прав (scopes). В базе хранится только SHA-256 токена.
- API описан в [OpenAPI](05-api/openapi.yaml).
- Агент без нужного права получает 403, с неверным токеном 401.

**US-12 (M).** Как Герман, я хочу, чтобы агент не затирал мои ручные правки.
- Обновление вакансии агентом требует заголовок `If-Match` с версией. Если я изменил запись после чтения агентом, API отвечает 412 Precondition Failed, агент перечитывает запись и пересчитывает изменения. Без заголовка API отвечает 428.
- Агент не возвращает вакансию на более ранний этап: из «собеседования» обратно в «подана» не переводит (422, код `status-downgrade`). Отказ и резерв ставятся с любого этапа.

**US-13 (M).** Как Герман, я хочу видеть журнал запусков агентов, чтобы знать, когда данные обновлялись в последний раз и не упал ли прогон.
- Для каждого запуска: агент, начало, конец, статус, сколько записей создано и изменено, ошибка.
- В шапке приложения: «обновлено ЧЧ:ММ», если последний успешный прогон старше 12 часов, строка становится жёлтой.

**US-14 (M).** Как ИИ-агент, я хочу повторять запрос после сбоя сети без дублей.
- Письма, дела и учебные работы записываются по естественному ключу (`PUT` по `source` и `externalId`).
- Для `POST` поддерживается заголовок `Idempotency-Key`, повтор с тем же ключом в течение 24 часов возвращает тот же ответ.

#### Эпик E8. Доступ и офлайн

**US-15 (M).** Как Герман, я хочу, чтобы данные видел только я.
- Вход по одноразовой ссылке на почту или по passkey. Регистрация новых пользователей выключена.
- Политики RLS на всех таблицах: строка видна, только если `owner_id = auth.uid()`.

**US-16 (M).** Как Герман, я хочу открыть «Сегодня» без сети (в метро, в аудитории с плохим сигналом).
- Приложение ставится на экран «Домой» (manifest и service worker).
- Последние загруженные данные доступны на чтение без сети, в шапке видна пометка «офлайн, данные на ЧЧ:ММ».
- Запись без сети в MVP недоступна, кнопки неактивны. Очередь офлайн-записей в v1.2.

#### Эпик E9. Аналитика

**US-17 (S).** Как Герман, я хочу видеть, какие каналы поиска дают ответы, чтобы тратить время на лучшие.
- Таблица каналов: подано, живых ответов, тест или собес, доля ответов. Автоответ ответом не считается.
- Скорость: дни от подачи до первого живого ответа по компаниям.

#### Эпик E10. Переход с v0

**US-18 (M).** Как Герман, я хочу перенести все данные со страницы v0 без потерь, чтобы не начинать с нуля.
- Скрипт миграции читает коллекции v0 (`apps`, `inbox`, `study`, `tasks`, `cards`, `schedule`) и пишет их через API.
- После миграции число записей в каждой таблице совпадает с v0. Расхождения попадают в отчёт.
- v0 остаётся доступной только на чтение 2 недели, потом архивируется.

### 2.3 Что не делаем (Non-Goals)

- Не отправляем письма, сообщения и отклики от имени Германа. Ни агенты, ни приложение. Действие всегда делает человек.
- Не делаем автоотклик на вакансии.
- Не заменяем Obsidian: подробные заметки и шпаргалки остаются там, пульт даёт ссылку.
- Не делаем многопользовательский режим в MVP. Схема данных к нему готова (`owner_id`), но регистрации, ролей и 152-ФЗ-локализации нет.
- Не делаем нативное приложение для App Store.
- Не встраиваем чат с ИИ внутрь приложения.
- Не храним полные тексты писем, только суть до 500 символов.

## 3. Требования к ИИ-части

ИИ в продукте работает снаружи: задачи Claude Code по расписанию. Приложение само моделей не вызывает.

### 3.1 Что делают агенты

| Задача | Вход | Выход в пульт |
| --- | --- | --- |
| Классификация письма | тема, отправитель, текст | `message.kind` |
| Привязка письма к вакансии | компания, роль, ссылка | `message.vacancy_id` |
| Извлечение срока | текст письма | `message.deadline` |
| Суть и действие | текст письма | `summary` до 500 символов, `action` до 200 |
| Статус отклика на hh.ru | страница откликов в браузере | `vacancy.status` |
| Карточки после собеседования | заметка «Подготовка <Компания>» | новые `flashcard` |
| Расписание | raw JSON из ЛАД | снимок `schedule_snapshot` |

Инструменты агентов: коннектор Gmail, браузер Edge с расширением Claude (hh.ru), HTTP к GitHub raw (ЛАД), API пульта.

### 3.2 Оценка качества

- Раз в неделю агент выбирает 20 последних записей `message`, я отмечаю верность типа, вакансии и срока.
- Цели: тип письма не меньше 90% верных, привязка к вакансии не меньше 95%, срок у приглашений и тестов 100%.
- Ложный «отказ» недопустим: тип `reject` ставится, только если в письме есть явный отказ. При сомнении ставится `info` с пометкой.
- Результаты оценки пишутся в заметку Obsidian `06 ИИ-агенты/Качество пульта.md`.

### 3.3 Защита от ошибок ИИ

- Текст писем и страниц для агента это данные, а не инструкции (защита от prompt injection). Инструкции агент берёт только из своего промпта.
- В API нет методов, которые что-то отправляют наружу. Даже взломанный агент может только записать данные в пульт.
- Все поля проверяются по схеме: длина, перечисления, формат дат. Неизвестные поля отклоняются (422).

## 4. Технические требования

### 4.1 Архитектура

Стек выбран в [ADR-001](06-decisions/ADR-001-stack.md): React, Vite и TypeScript на клиенте, Supabase (Postgres, Auth, Data API, Edge Functions) на сервере.

Потоки данных:
1. Агент читает внешние источники и вызывает `ingest` API с токеном.
2. Edge Function `ingest` проверяет токен и права, валидирует тело, пишет в Postgres, ведёт историю и журнал запуска.
3. Если запись требует внимания, триггер ставит уведомление в очередь, функция `notify` отправляет Web Push.
4. PWA читает и меняет данные через Data API (PostgREST) с JWT пользователя. Доступ ограничивают политики RLS.
5. Раз в сутки `pg_cron` запускает `schedule-sync`, которая забирает расписание из ЛАД.

Диаграммы: [C4 уровень 1](02-architecture/c4-context.md), [C4 уровень 2](02-architecture/c4-containers.md), [последовательность синхронизации](04-processes/processes.md#3-последовательность-запись-письма-агентом).

### 4.2 Точки интеграции

| Система | Направление | Способ | Кто вызывает |
| --- | --- | --- | --- |
| Gmail (основной ящик) | чтение | коннектор Gmail в Claude | агент |
| hh.ru | чтение | браузер Edge с расширением Claude (у соискателей нет открытого API откликов) | агент |
| ЛАД, ветка `data` на GitHub | чтение | HTTPS GET raw JSON | `schedule-sync` и агент |
| Google Календарь | запись событий | коннектор Calendar | агент |
| Obsidian | запись сводок | файлы на диске D: | агент |
| Web Push (Apple, Google) | отправка | протокол Web Push, ключи VAPID | `notify` |
| Telegram Bot API | отправка, запасной канал | HTTPS | `notify`, v1.2 |

### 4.3 Нефункциональные требования

| Код | Требование |
| --- | --- |
| NFR-01 | LCP экрана «Сегодня» не больше 2,5 с на профиле Lighthouse Mobile. Бандл JS первого экрана не больше 200 КБ gzip. |
| NFR-02 | Ответ `ingest` API не больше 800 мс на 95-м перцентиле для одиночной записи. |
| NFR-03 | Пакетная запись: до 50 объектов в запросе, атомарно. |
| NFR-04 | Доступность Lighthouse Accessibility не меньше 95, контраст текста WCAG 2.2 AA, всё управляется с клавиатуры. |
| NFR-05 | Светлая и тёмная тема по системной настройке. Ширина экрана от 360 px без горизонтальной прокрутки. |
| NFR-06 | Все даты и время в Europe/Moscow. В базе `timestamptz`, даты без времени в `date`. |
| NFR-07 | Язык интерфейса русский. Длинные тире в интерфейсе не используются. |
| NFR-08 | Раз в неделю агент выгружает базу в JSON на диск D: (на бесплатном тарифе Supabase нет автоматических бэкапов). Хранятся последние 8 выгрузок. |
| NFR-09 | Журнал запусков агентов и уведомлений хранится 90 дней. |

### 4.4 Безопасность и персональные данные

- Вход только для одного адреса, регистрация выключена в настройках Supabase Auth.
- RLS включён на всех таблицах, политика `owner_id = auth.uid()`. Ключ `service_role` есть только у Edge Functions и никогда не попадает в клиент или к агентам ([ADR-003](06-decisions/ADR-003-agent-ingest-api.md)).
- Токены агентов: 32 случайных байта, в базе SHA-256, срок жизни 180 дней, отзыв флагом `is_active`.
- Ограничение частоты: 60 запросов в минуту на токен, дальше 429.
- Заголовки на клиенте: Content-Security-Policy без `unsafe-inline` для скриптов, HSTS.
- Персональные данные. 152-ФЗ не действует на обработку данных физлицом исключительно для личных и семейных нужд (ст. 1 ч. 2 п. 1), если права субъектов не нарушаются. Пульт личный, но в нём есть данные третьих лиц: имена и адреса рекрутеров. Поэтому храним минимум: имя отправителя, адрес и суть письма, без полного текста. При переходе к многопользовательской версии нужна локализация базы в РФ (ст. 18 ч. 5) и переезд с Supabase Cloud, см. раздел 5.

### 5.2 Риски
