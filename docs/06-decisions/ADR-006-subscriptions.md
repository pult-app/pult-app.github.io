# ADR-006. Трекер подписок: якорная дата, напоминания в базе, календарь

- Статус: принято
- Дата: 12.10.2026

## Контекст

Герман хочет знать, когда и какая подписка спишется. Раньше такие платежи жили делами со сроком (`task`, вид «деньги»): агент создавал дело по письму вроде «Продление iCloud+ 26.10». У дела нет суммы и периода, нельзя посчитать расходы в месяц, а после списания дело приходится заводить заново.

## Варианты

| Вариант | Что не так |
| --- | --- |
| Оставить дела-напоминания | Нет суммы, периода и итогов, каждое списание нужно создавать заново |
| Хранить заранее сгенерированные строки по каждому будущему списанию | Нужна фоновая задача, строки устаревают и расходятся с реальностью при смене даты |
| Подписка с якорной датой, следующие списания считаются по правилу | Чуть сложнее арифметика дат, зато запись не устаревает и одна на подписку |
| Готовый сервис (Bobby, Rocket Money, Copilot) | Данные о платежах уходят наружу, нет связки с агентами, календарём и пушами пульта |

## Решение

- Таблица `subscription`: сумма, валюта, период (`unit` и `every`: раз в `every` недель, месяцев или лет), якорная дата `next_charge_on`, состояние (`active`, `trial`, `paused`, `cancelled`), категория, срок напоминания.
- Следующее списание не хранится. Оно считается как якорь плюс k периодов, месяцы и годы от якоря, день месяца обрезается по длине месяца (31 января, 28 февраля, 31 марта). Правило реализовано трижды: TypeScript в приложении (`billing.ts`), копия в Edge Function календаря, SQL-функция `private.next_charge`. Расхождений нет: тест сверяет TypeScript-копии, а SQL проверен на 4160 комбинациях против TypeScript.
- Напоминания: функция `private.queue_charge_reminders` по `pg_cron` каждый день в 9:00 по Москве кладёт пуш в `notification` (дальше работает прежняя цепочка `notify`). Журнал `subscription_reminder` даёт одно напоминание на одно списание. Журнал вынесен в отдельную таблицу, чтобы не менять `row_version` подписки.
- Календарь: ICS-подписка получает события списаний на 90 дней вперёд, а ярлык iOS ближайшее списание третьей строкой.
- Агенты пишут через `PUT /subscriptions/{key}`. Отмену и паузу, которые поставил Герман, агент не возвращает; если запись правил Герман, агент меняет только цену, валюту, дату и состояние (письма сервиса точнее, чем память).
- Валюты не пересчитываются: курс создал бы ложную точность. Итоги по каждой валюте отдельно, основная валюта (рубли) показывается крупно.
- В приложении и API нет физического удаления: подписку закрывают состоянием «отменена».
- Приложение выкладывается раньше миграции без падений: отсутствие таблицы определяется по коду PGRST205 и вкладка «Деньги» объясняет, что делать.
- Дело вида «деньги» с названием подписки в день её списания в повестке «Сегодня» не дублирует строку списания.

## Последствия

- Нужна миграция `0011_subscriptions.sql` и новые права токена агента (`subscriptions:read`, `subscriptions:write`). Без них вкладка «Деньги» работает вручную, агент записывать подписки не может.
- Пока в базе нет таблицы, календарь и ярлык отдают прежнее содержимое (запрос подписок вернёт ошибку, функция её игнорирует).
- Задача `funnel-sync` после выдачи прав получает шаг «подписки из писем»: искать чеки и письма о продлении и делать `PUT` по ключу сервиса. До этого агент создаёт дела вида «деньги», как раньше.
- Если появятся подписки в других валютах, потребуется решение по курсам: это отдельный ADR.
